# Maw3ed — architecture

One Next.js app on free tiers. Route handlers validate and authorise, the service layer holds the logic, and
repositories are the only code that touches Prisma. The two hard guarantees live in Postgres; the slot logic is a pure function.

```
               ▼                         ▼                              │

 │ Services         src/server/services  booking · reminders · waitlist │──► Resend (EmailProvider)

                                ▼
              Neon Postgres: exclusion constraint (no double booking)
                             unique (appointmentId, kind, channel) (no double send)
```

## Request lifecycle
1. `withRoute(config, handler)` creates `requestId`, a child pino logger, and parses params/query/body/headers with Zod (`.strict()`).
2. Guard by mode: `session` (cookie → `Session` → Membership → `ctx.businessId`, `ctx.role`), `public` (no auth; the service resolves the slug),
   `token` (HMAC verify → `ctx.token`), `cron` (constant-time `x-cron-secret`).
3. Handler calls one service. Services enforce roles and pass `ctx.businessId` to repositories.
4. Errors → `{ error: { code, message, fields } }` with the status table in the `api-endpoint` skill. Unexpected errors (non-AppError, or an AppError with status 500 or above except `SERVICE_BUSY`) → 500, logged with pino and reported to Sentry (see "Error monitoring" in the key decisions); 4xx are never reported.

## Engineering heart

### 1. Slot generation (`domain/slots.ts`)
`generateSlots(input) → Slot[]`, pure. Input: service duration and buffer; for each eligible staff member their weekly
intervals (`weekday`, `startLocal`, `endLocal`), time off (UTC), busy intervals (`startAt → blockedUntil`); `slotStepMin`,
`minNoticeMin`, `bookingWindowDays`, `timezone`, `now`, and a `from`/`to` range.
For each local day in range and each staff member:
1. Build that day's working intervals in local time with Luxon (`DateTime.fromObject({...}, { zone })`) and convert to UTC instants.
   A wall time that doesn't exist (Beirut springs forward at 00:00) moves forward; a repeated hour uses the earlier offset. Tests pin this.
2. Subtract time off and busy intervals (interval arithmetic on epoch ms).
3. Walk each free interval from its start in `slotStepMin` steps, aligned to the local step grid; emit `start` when
   `start + duration + buffer ≤ interval.end` and `start ≥ now + minNotice` and `start < windowEnd`.
4. "Anyone": union of starts across staff; each slot keeps the candidate staff ids. On booking, the service picks the free
   candidate with the fewest bookings that local day (ties → stable order by staff id).
**Known limit (after-midnight hours):** working hours are per weekday and an interval never crosses midnight, so a night shift is stored as `start–24:00` plus `00:00–end` on the next weekday (the hours editor's "open past midnight" assistant writes both). A booking therefore cannot span midnight: the last start of a 60-minute service stays 23:00 even when the next day opens at 00:00.
**Merged hours blocks (PR-3).** Because a service plus its buffer must fit inside ONE free interval, two touching blocks (09:00-17:00 and 17:00-22:00) behave as two: a 60-minute service could not start at 16:15, 16:30 or 16:45. The slot engine is unchanged; instead the pure `lib/setup/hoursMerge.ts` (`mergeDayIntervals`, `mergeWeekIntervals`: sort, union touching and overlapping blocks of the SAME weekday, never more blocks than given, idempotent) is applied in the Hours editor (when a week loads and when Apply is pressed) and on the server in `hoursService.replace` and `hoursService.copyTo` (after validation, so a real overlap is still a 400). A real break (12:00-13:00 free) stays two blocks. Existing stored data stays split until its next save (no data change was made). **Remaining limits:** blocks on DIFFERENT days are never merged (the Sunday-to-Monday midnight split, Monday 09:00-24:00 plus Tuesday 00:00-02:00, stays as two rows), so a booking still cannot cross midnight.
The repository loads all inputs for the range in a fixed number of queries (no N+1), keeping NFR-09 (< 300 ms p95).
**F33 speed:** the profile showed ~60 % of a request in Luxon `IANAZone.offset` (an Intl format on every call, thousands per request). The generator now memoises zone offsets per hour bucket (a bucket that contains a transition is never cached, so DST answers still come from Luxon), memoises local-to-UTC conversions, walks the calendar days once per call, and scans only the time-off/busy intervals that overlap each working interval. Output is proven identical to the pre-change code by `tests/unit/booking/slots.f33.equivalence.test.ts`. These are memoised pure functions of the immutable tz database: no business data is cached.

### 2. No double booking (Postgres exclusion constraint)
The hand-written migration `appointment_no_overlap` (see the `db-migration` skill) excludes overlapping
`tstzrange(startAt, blockedUntil, '[)')` per `staffId` while the status is `BOOKED`, `CONFIRMED` or `PENDING_PAYMENT` (a 15 minute deposit hold).
- The booking service re-checks availability first, to give a friendly answer, then inserts. Postgres `23P01` → 409 `SLOT_TAKEN` + fresh slots.
- `Idempotency-Key` header: stored on `Appointment.idempotencyKey` with unique `(businessId, idempotencyKey)`; a repeat returns the first booking.
- One insert path for public bookings, front-desk bookings, waitlist claims and deposits.
- Cancelling sets `CANCELLED` / `LATE_CANCEL`, which drops the row out of the constraint and frees the slot.

### 2b. Outcomes: the no-show grace period and Excuse (PR-2)
`domain/outcomes.ts` (`planOutcome`, `planExcuse`) is pure; the clock is injected.
- **Grace period.** Leaving BOOKED / CONFIRMED frees the slot in `appointment_no_overlap`, so a premature No-show would let a walk-in take the time of a client who is only late. `NO_SHOW` from an unmarked booking is therefore allowed only from `startAt + NO_SHOW_GRACE_MIN` (10 minutes, a fixed constant, not a business setting). Earlier: 409 `NO_SHOW_TOO_EARLY` with `error.data.availableAt` (ISO instant). `LATE_CANCEL` is allowed from `startAt` (the client said they are not coming); `ATTENDED` still needs `endAt <= now`. PR-3 closed a loophole (owner chose Option 2): the grace guards EVERY move into NO_SHOW, so a correction from a staff-marked LATE_CANCEL (or from ATTENDED) to NO_SHOW is held back until `startAt + 10 min` as well (same `grace_period` plan kind, 409 `NO_SHOW_TOO_EARLY`); otherwise staff could mark LATE_CANCEL at +1 min and correct it to NO_SHOW at once. A LATE_CANCEL written by the cancel link stays final (conflict). Every other correction (for example NO_SHOW to LATE_CANCEL or to ATTENDED) is never held back. The Mark outcome queue (ended, unmarked appointments) and its badge are unchanged.
- **Excuse.** `POST /api/appointments/{id}/excuse` (OWNER, STAFF; strict empty body; no reason is accepted or stored, in line with the privacy rule). One repository transaction: the appointment row is locked `FOR UPDATE`, the pure plan decides, the status becomes `CANCELLED`, and the matching `Client` counter (`noShows` for NO_SHOW, `lateCancels` for LATE_CANCEL, whether staff or the cancel link set it) is decremented by one and never below 0. A cancel-link `cancelledAt` / `cancelledVia` is kept; a staff-marked outcome gets `cancelledVia = STAFF`; `outcomeMarkedById/At` stay as the audit trail. Already CANCELLED: 200 no-op, so two concurrent excuses decrement once. BOOKED, CONFIRMED, ATTENDED, PENDING_PAYMENT: 409 `CONFLICT`. The log line carries ids only.
- **Guarantee 1 is untouched.** The constraint's active set is `BOOKED`, `CONFIRMED`, `PENDING_PAYMENT` (migration `20261031090100_deposit_overlap_constraint`). NO_SHOW, LATE_CANCEL and CANCELLED are all outside it, so an excuse neither frees nor takes a slot; it also does not offer the waitlist anything (the slot is in the past).
- **Who reads what after an excuse.** The deposit gate (`depositRequired`, `clientRepo.noShowsByPhone`) and the repeat-no-show badge read `Client.noShows`, so a client at the threshold stops being asked for a deposit right away. The client history and the appointment page show the status (CANCELLED). The pilot report is computed from appointment statuses (`domain/pilotMetrics.ts`: CANCELLED is excluded, NO_SHOW counts in the numerator): an excused no-show **leaves the no-show numerator and the denominator of the week it happened in**, so a past week's rate can change after the fact. The pilot definition text says so, and the CSV export shows the booking as CANCELLED.

### 3. Reminders that never send twice
1. **Create**: the booking transaction inserts `ReminderJob` rows: `BOOKING/EMAIL` (immediately), `H24/EMAIL`, `H2/EMAIL`, `H24/WHATSAPP`, `H2/WHATSAPP`,
   skipping kinds already past (booked < 24 h ahead → no H24; < 2 h → no H2). Unique `(appointmentId, kind, channel)`.
   F68: a PUBLIC booking made < 2 h ahead also gets one `LATE/WHATSAPP` row (due at the booking time, never an EMAIL row; front desk and waitlist claims get none). It stays on the receptionist list until the appointment starts, with a confirmation-style text, and the email runner skips an EMAIL LATE row (`whatsapp_only`) if one ever appears. The BOOKING email carries Cancel only when an H24 reminder follows (lead >= 24 h), else Confirm and Cancel (`bookingEmailPlan`).
2. **Trigger**: `POST /api/jobs/reminders` every 5 min (cron-job.org + GitHub Actions backup). It works on "whatever is due", so late or doubled triggers are harmless.
3. **Requeue**: `SENDING` rows locked more than 10 min ago → `PENDING` (crash recovery).
4. **Claim**: one `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING *`, at most 50 rows.
5. **Re-check**: appointment no longer active, or the window has passed (H24 after the 2 h mark; H2 within 15 min of start) → `SKIPPED`.
6. **Send**: `EmailProvider.send({ idempotencyKey: job.id, … })`. Resend returns the original result for a repeated key within 24 h.
7. **Record**: `SENT` + `providerMessageId` + `sentAt`; failure → `PENDING` with `nextAttemptAt` backoff (1, 5, 15 min); `FAILED` after 3 attempts.
8. **WhatsApp** rows are never sent by the server: they appear in `/api/reminders/whatsapp-due` once due, and
   `mark-sent` runs `UPDATE … WHERE id=? AND status='PENDING'`; zero rows updated → 409 with `sentBy`/`sentAt`.
9. **Email budget**: a daily count of SENT emails; warn at 80 (NFR-10); at ≥ 95, BOOKING confirmations are skipped before any reminder.

### Waitlist
Cancel (link or staff) → `waitlist.onSlotFreed(appointment)` → match `WaitlistEntry` rows (same service, date range covers the slot,
staff null or equal, status OPEN) ordered by `createdAt` → create `WaitlistOffer`s for the first batch of 3 (unique per entry per freed slot),
`expiresAt = min(now + 30 min, slotStart − minNotice)` → email with a signed claim token. Claim → booking service (same insert, so the
first claim wins and others get 409) → the offer is CLAIMED, the entry FULFILLED. `POST /api/jobs/waitlist-expiry` expires offers and
offers the next batch until the slot is inside the minimum notice, and first sweeps lapsed deposit holds (each frees a slot and offers it at once).
A claim first takes an atomic reservation on the entry (`claimingOfferId` / `claimingAt`, 60 s lease) so one entry cannot book two slots at the same instant;
a claim that needs a deposit leaves the entry reserved while its hold is live (see the key decisions).
Staff side (F65): `/app/waitlist` shows `GET /api/waitlist` (OPEN entries only, oldest first = the order of `openCandidates`, capped at 100 plus a real `total`) and removes with `DELETE /api/waitlist/{id}`. The endpoint is the privacy boundary: `client` is `{ firstName, phone }` where the phone is masked on the server by `maskPhone` (`domain/waitlistPrivacy.ts`, always `•••• ••• ddd`), and no email or full number is ever selected into the response.

### Public directory: categories, areas and the index (PR-1, PR-2)
- Filters are `listed AND ready` plus `search` (ILIKE), `category` (`lower(category) = lower(?)`) and `area` (equality); order `name, id` keyset. Atomic listing (PR-2): `businessService.update` turns `listed` on through `businessRepo.updateGuarded`, one transaction with the business row locked `FOR UPDATE`, so the category/area check and the write see the same row (a concurrent `{ area: null }` cannot slip in between); a business that is already listed stays grandfathered.
- **Legacy free-text categories** (rows saved before the fixed list, e.g. `Salon`) match no category key, so they appear only under "All categories" in `/directory` (they are still shown on their card as typed, and the exact-text `?category=Salon` link still works). Settings shows them as "Current: <text>" with the hint "Pick a listed category to appear in the category filters". No data is rewritten by code: the owner picks a listed category when ready.
- **Index `Business_listed_area_category_idx (listed, area, category)`: kept.** Checked with `EXPLAIN (ANALYZE)` on a scratch schema with 5,000 generated businesses (3,038 listed, services, staff and hours for each): the area filter and the area + category filter both use it (Bitmap Index Scan on `listed = true AND area = ?`, about 0.3 to 1.4 ms). The category-only filter (`lower(category)`) and the ILIKE search cannot use it and sequentially scan (2 to 4 ms at that size); a partial `(lower(category)) WHERE listed` index would be picked for the category-only query but saves about 1 ms at 5,000 rows, so it is not worth a migration at pilot scale (dozens of businesses). Revisit when the directory passes a few thousand listings.

### Marketplace data: booking reference and live aggregates (PR-6)
**Booking reference.** `Appointment.reference` (nullable, unique index `Appointment_reference_key`; existing rows keep NULL, nothing is backfilled). It is generated in `appointmentRepo.create`, i.e. inside the ONE insert that public booking, front desk, waitlist claim and deposit hold all use (`appointment_no_overlap`, the status set and the 23P01 to 409 `SLOT_TAKEN` mapping are untouched). `domain/reference.ts` (pure, the random source is injected) builds 6 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 symbols, no O/0/I/1/L) with `crypto.randomInt`. A unique violation aborts the transaction, so the whole insert is retried with a new code, up to 5 times, and then 503. The repository tells the three unique rules apart by the names in the error (`violatedNames` in `http/errors.ts`: `meta.target`, the driver-adapter constraint index or fields): only the `reference` index retries; the idempotency key (`businessId, idempotencyKey`) still resolves to the replay of the first booking and returns its stored reference; 23P01 still means the slot is gone. The code is a label, not a credential: no route looks a booking up by it and no token contains it. Shown on the booked step (`BookedView`), the BOOKING e-mail (a "Reference" row in the details, en and ar, text and HTML, read from the stored column so a retried send is byte-identical), the client link page (`/l/[token]`) and the owner/staff appointment page and API. Deliberately NOT in the barber DTOs (their exact field picks are unchanged: a barber identifies a visit by time, service and client, and the client quotes the code to reception) and not in the CSV pilot export. The booked step in this repo is `BookedView` inside the booking flow (there is no `/b/[slug]/booked/[token]` route). Production gets the column from the Vercel build (`prisma migrate deploy`) after merge.

**"Next free" (exact definition).** `domain/nextFree.ts`, pure, built on the unchanged `generateSlots`: a business's next free is the earliest bookable start of its SHORTEST active service (ties: lower price, then name, then id) that at least one active, bookable staff member with working hours performs, searched over the next 7 local days (today included) in the business's own timezone, with the engine's own rules for minimum notice, booking window, weekly hours, time off, existing bookings (a lapsed deposit hold does not block), buffers and DST. It generates one local day at a time and stops at the first day that has a slot, which is why it costs a few milliseconds per business. `freeTimes` are up to 4 distinct start instants (staff merged) on that first day, as UTC ISO strings; the client formats them with the returned `timezone`. Null when the business has no active service that anyone performs, or nothing is free in the window. `when=yyyy-MM-dd` uses the same rule restricted to that one local day.

**Endpoints.** `GET /api/public/directory` adds `include=nextFree` (default off: the old shape and cache behaviour are unchanged), `service` (ILIKE contains over ACTIVE service names, parameterised, `%`/`_` literal) and `when`. With `include` or `when` the page is at most 12 (default 12; a larger `limit` is 400). `when` scans candidates in the directory order in batches of 12, up to 36 per request, computing slots for each batch, and returns the matches found so far; `nextCursor` points after the last candidate examined, so a page may hold fewer than `limit` items (even none) while `nextCursor` is set: clients keep paging until it is null. `GET /api/public/categories?area=` returns `{ categories: [...] }` for every key of `CATEGORY_KEYS` (seven, `other` included; zero places give `places: 0`, `fromPrice: null`, `nextFree: null`, `popularServices: []`): places and cheapest price are one SQL aggregate, popular services one ranked query (a service counts once per business offering it, case-insensitive name, top 5 with its cheapest price), `nextFree` is the earliest instant among the FIRST 6 businesses of the category in directory order (a bounded batch, so a category with more than 6 places may show a later time than its true earliest; documented trade-off). Both are public data of `listed` and ready businesses only (the batch loader drops unlisted ids a second time) and carry no e-mail, phone, staff, client or appointment data (raw-JSON test). `Cache-Control: public, s-maxage=60, stale-while-revalidate=300`.

**Cost control.** All slot inputs for a bounded set of businesses are batch-loaded in a fixed seven statements (`availabilityRepo.loadMany`: businesses, active services, bookable staff plus their services (Prisma sends the nested relation as a second statement), hours, time off, busy appointments), never per business; the engine then runs with at most 4 businesses in flight (`mapLimit`, order preserved). Rate limit: a plain directory read is counted by `directory` (120 per 10 min); the costlier calls (`include`, `when`, and every `categories` request) are additionally counted by the new policy `directoryLive` (60 per 10 min per IP, soft policy like the other cacheable reads). The directory service consumes it (so a request is counted once); the categories route declares it.

**Measured** (`scripts/perf/directory-live.ts`, local Postgres 16 in Docker, scratch schema, 60 listed businesses with 3 services, 3 staff with Monday-Saturday hours and 28 bookings each = 5,040 appointments; the machine was also running other work, so the numbers moved by about 2x between runs):

| Call | SQL statements | First call in a fresh process | Warm median / p95 |
|---|---|---|---|
| `directory` page of 12 (no include) | 1 | 124 to 268 ms | 3 to 8 ms / 6 to 12 ms |
| `directory?include=nextFree` (12) | 8 | 129 to 373 ms | 18 to 48 ms / 28 to 71 ms |
| `directory?when=<tomorrow>` (scan up to 36) | 24 | 29 to 80 ms | 28 to 72 ms / 32 to 95 ms |
| `categories` | 10 | 32 to 104 ms (first ever: about 260 ms) | 86 ms / 96 to 107 ms |
| `categories?area=beirut` | 10 | 21 to 48 ms | 21 to 48 ms / 27 to 60 ms |

With 300 businesses the same calls stay in the same range (page 13 ms, include 101 ms, categories 266 ms in the first run): the cost is bounded by the 12 / 36 businesses whose slots are computed, not by the directory size. Everything is far below the 1.5 s line, so the horizon stays 7 days. An early version generated all 7 days for every business and took about 250 ms for the 36 businesses of `categories`; stopping at the first day with a slot made it about 86 ms. The statement counts are fixed (no N+1), measured with a patched `pg` client: 8 = 1 list + 7 batch-load statements; `when` = 3 batches x 8 = 24; `categories` = 3 SQL aggregates + 7 = 10.

### Staff (barber) login (PR-4)
- Identity: `User.phone` (E.164, unique) next to an optional `User.email`; the CHECK `user_has_identity` keeps at least one. Role `PRACTITIONER` (Membership) is in NO route's roles list: default-deny. Self-service routes (logout, change-password, sign-out-others, me, resend-verification) have no list on purpose; `tests/unit/auth/routeRoles.test.ts` scans every route source and `tests/integration/roles.practitioner.test.ts` calls every session route with a real PRACTITIONER session. PR-5 adds four narrow scoped routes explicitly (next section).
- Activation: `ActivationToken` (not `Invite`: the StaffMember already exists, the owner chose the phone, and the secret becomes a first password). Token = 32 random bytes base64url, only sha256 stored, 72 h, single use (conditional UPDATE inside the activation transaction, which also creates or re-uses the phone user, sets the hash, grants the membership, links the StaffMember and inserts the session). One open link per staff member (partial unique index). Every unusable link is the same 404; the page reveals nothing else.
- Login: `parseLoginIdentifier` (pure) decides email or phone; the guard key is the canonical form, so every spelling of one number shares a bucket; unparsable text and unknown phones take the dummy-hash path and give the same 401.
- Revocation: reset access and turn off delete the user's sessions in the business in the same transaction as the link or membership change (`revokeStaffLogin` in `staff.repo.ts`); deactivating a StaffMember does the same. The role is re-read from Membership on every request, so a deleted membership ends access at once.
- No email reset for phone-only accounts; forgot-password finds no email and sends nothing (same 200). Lock order: staff row, then user row, then the user's sessions and memberships.
- Lock order (PR-5 fix): `activate` reads the token WITHOUT a lock, locks the staff row, and only then claims the token, the same order as `issueLink` and `turnOff` (staff row first, token rows second). The PR-4 order (token row, then staff row) could deadlock against a reset or turn-off; `tests/integration/staffLogin.concurrency.test.ts` holds the staff lock from a second connection to prove it cannot, and races activate, reset and turn-off for a no-5xx run.
- Activation links hold the person's E.164 phone, so the daily cleanup job (`/api/jobs/cleanup`) deletes links used, or expired unused, more than 7 days ago. The login itself lives in User / Membership; nothing is kept "for audit".
- The activation link is a bearer secret in the URL: `/activate/*` sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; the owner sees the link once (the create response) and it is never logged.


### The barber's own screens (PR-5)
A PRACTITIONER (barber login) sees and marks outcomes on THEIR OWN appointments only: no booking, no cancel, no edit, no excuse. They see the client's **first name and phone** (Call and WhatsApp buttons), never the e-mail, the surname, the booking contact override, reminder details, counters, no-show flag or history, and never another staff member's or client's data (decision: the owner view's "repeat no-show" badge is NOT shown to the barber).

**Scope.** `src/server/domain/scope.ts` (pure): `scopeFor(role, linkedStaffId)` is `{ kind: 'all' }` for OWNER and STAFF, `{ kind: 'own', staffId }` for a PRACTITIONER with a linked, active staff member, and `null` otherwise (never "all"). `resolveScope(ctx)` (`services/scope.ts`) reads the link with `staffRepo.linkedStaffId(businessId, userId)` where both ids come from the SESSION, and throws 403 for `null` (login turned off, person deactivated, link removed). Every scoped repository method takes a REQUIRED `scope` argument and spreads `scopeWhere(scope)` into its `where` (`outcomeRepo.listForDay / listQueue / countQueue / markOutcome / listColumns`, `appointmentRepo.findByIdInScope`), so a missing scope is a compile error and a foreign id is a plain 404 (never 403, never data). One service, one query: the owner and the barber share the code; only the scope and the DTO differ (`barberClient` is the single place that builds the barber's client part).

| Route | Roles | Scoping and shape for a PRACTITIONER |
|---|---|---|
| `GET /api/dashboard/today?date=` | OWNER, STAFF, PRACTITIONER | only the linked staff member's appointments and own column; client = `{ name (first), phone }`; stats = `{ appointments }` only; `outcomesToMark` = their own queue; no waitlist, WhatsApp or reminder fields |
| `GET /api/appointments/{id}` | OWNER, STAFF, PRACTITIONER | own appointment only (another barber's, another business's or unknown id: 404); first name, phone, service, time, status, `confirmedAt`; no e-mail, contact override, reminder line, price, source, counters |
| `PATCH /api/appointments/{id}/outcome` | OWNER, STAFF, PRACTITIONER | own appointment only (404 otherwise, nothing changes); same rules as the owner (10 min no-show grace, Attended after the end, link late cancel final); counters change once; response client = first name + phone |
| `GET /api/outcomes/queue` | OWNER, STAFF, PRACTITIONER | own ended appointments only, `count` is theirs (it feeds the tab badge, so `/api/dashboard/summary` stays closed); client = first name + phone |

**The allow-list for a PRACTITIONER is exactly nine handlers:** the five self-service routes (`POST auth/logout`, `auth/change-password`, `auth/sign-out-others`, `auth/resend-verification`, `GET me`) plus the four above. Every other session route answers 403 (`tests/integration/roles.practitioner.test.ts` calls all of them with a real session; `tests/unit/auth/routeRoles.test.ts` scans every route source: the number of handlers found equals the number of `withRoute(` calls, comments are stripped before the `roles: [` check so a comment cannot mask a missing list, and PRACTITIONER may appear in exactly the four scoped routes, each listing `['OWNER', 'STAFF', 'PRACTITIONER']`).

**Pages.** The barber's shell is the normal `AppShell` with `practitioner` set: bottom tab bar Today / Outcomes / Account (no More, no floating New booking), a three-link sidebar at `lg+` (no business navigation, no New booking), one badge (their outcomes to mark). Allowed pages are exact patterns in `src/lib/auth/practitionerPaths.ts` (`/app/today`, `/app/outcomes`, `/app/appointments/[id]`, `/app/account`); `/app` and everything else lead to `/app/today`. **Hardening in PR-6.** (1) Every page under `src/app/app` must call `assertPractitionerPath()` with the path derived from its own file location (a page asserting another path fails the unit test; a nested layout must too; loading / error files may not import server data). (2) Every appointment read in `appointmentRepo` takes a required `scope` (`findById`, `list`, `reminderSources`; owner paths pass `ALL_SCOPE` explicitly), except the named token / pay / replay lookups (`findByIdempotencyKey`, `findForLink`, `findForPay`, `businessIdOf`, `countByStaff`); the old unscoped `findById` and `findByIdInScope` are gone, the scope is applied last in `list` so a requested `staffId` cannot widen it, and `tests/unit/auth/scopedReaders.test.ts` fails if a PRACTITIONER-enabled service function calls an unscoped reader. The outcomes service's `toDto` requires its scope too. (3) **Timing parity of the refusals** (`scripts/perf/barber-timing.ts`, 200 interleaved samples each after a warm-up, local Postgres, handler called in-process): before, an unlinked barber (403) stopped after the link lookup. Own id (200): 7 SQL statements, median 13.28 ms, p95 15.59 ms. Foreign id (404): 7 statements, 13.11 ms, p95 15.37 ms. Unlinked barber (403): 3 statements, 8.14 ms, p95 9.69 ms. A 5 ms (about 40%) gap is enough to tell "this login has no schedule" from "no such appointment" by timing. Fix: `resolveScopeForRead` makes the 403 path run the same row lookup first, with a scope that matches nothing (`NO_MATCH_SCOPE`), discard it and refuse; a failure of that stand-in never replaces the 403. After: 7 / 7 / 7 statements, median 12.24 / 11.98 / 12.14 ms, p95 14.61 / 14.22 / 14.22 ms. Only the appointment detail was equalised; the other barber routes (today, outcome, queue) answer a foreign id with an empty or 404 result after the same lookups and an unlinked barber with the same early 403 (documented, not changed: those lists never take an id from the barber, so there is no per-id oracle). Run it again after changing `get`.

### Signed links
`token = base64url(payload) + "." + base64url(HMAC-SHA256(LINK_SECRET, payload))`, payload `{ a: appointmentId | o: offerId, act: 'view'|'confirm'|'cancel'|'claim'|'pay', exp }`.
Verified with `timingSafeEqual`. Appointment links expire at `startAt`; offer links at `expiresAt`. The confirm and cancel pages load
with GET (no side effect) and act with POST, so email link scanners can't cancel an appointment.

## Key decisions
| Decision | Why |
|---|---|
| No cache of slot inputs or responses (F33) | Measured: after removing the Luxon offset cost the endpoint is bound by row decoding and the domain loop, not by the settings/staff/hours reads, so a TTL cache would save little and add stale-data risk. Slots stay uncached (no CDN/HTTP caching); the booking insert, its friendly re-check and the exclusion constraint always read fresh data. |
| Exclusion constraint in a hand-written SQL migration | The database is the referee; no application race can create an overlap. Prisma can't express it. |
| `FOR UPDATE SKIP LOCKED` + unique job key + provider idempotency key | Three independent layers make a duplicate send impossible to record, to claim and to deliver. |
| External scheduler (cron-job.org) instead of Vercel Cron | Vercel Hobby cron runs once a day; the job route is idempotent, so a backup scheduler is safe. |
| Custom session table instead of Auth.js | Credentials provider forces JWT sessions; we need server-side revocation and a business-scoped session. |
| Repository-owned transactions (`account.repo`, `invite.repo`) | Signup and invite-accept must commit several tables atomically; the Prisma transaction handle may only live in `src/server/repositories`, so those repos expose one method per transaction (an accepted exception to "one repo per entity"). |
| Soft email verification (L4) | A new account works at once (login, setup, public booking page); only inviting staff and `listed=true` need a confirmed address, rejected in the SERVICE layer with 409 `EMAIL_NOT_VERIFIED` (a state precondition like `NOT_READY`). Hard-blocking login would lose pilot owners on a spam-foldered email. A pre-existing user is verified by the migration; accepting a staff invite verifies the invitee (the link proves the inbox). |
| Account email tokens (`EmailToken`) | 32 random bytes base64url, only sha256 stored, VERIFY 24 h / RESET 1 h, single use by one conditional `UPDATE … WHERE usedAt IS NULL AND expiresAt > now`, a new token does NOT invalidate older ones (otherwise anyone could kill the link a user is about to click by asking again): at most 5 live unused tokens per user and kind are kept (the oldest are deleted), and a successful use deletes ALL the user's unused tokens of that kind. Trade-off: several valid links may coexist for at most 1 h (reset) / 24 h (verify), all single use. A failed send therefore never leaves a user without a working link. The emailed link opens a page with a button; only the POST changes state (mail scanners prefetch GETs). Tokens and passwords never appear in logs; those pages send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. |
| Forgot password never enumerates users (A1) | `POST /api/auth/forgot-password` does ONLY the rate-limit count before it answers; the user lookup, membership read, token issue, rendering and send all run in `afterResponse` (`after()`), so the response path is identical for known and unknown emails and latency cannot leak existence (a structural test asserts none of it has run when the response resolves). Per-email cap 5 / h: past it the same 200, nothing issued or sent, and NO per-email 429; the per-IP 429 (10 / h) is the same for every email. Failures after the response are logged, never surfaced. Accepted residual: a flood of requests for one address can fill its 5 / h budget and delay that user's reset up to an hour, but their already emailed links keep working. |
| Password reset and change revoke sessions (A1) | Reset deletes EVERY session of the user (all businesses), marks the email verified and kills other open reset links in the same transaction as claiming the token; change-password deletes the user's OTHER sessions and keeps the current one. A wrong current password is a 400 on `currentPassword` (a 401 would make the dashboard assume the session ended). Reset does not sign anyone in. |
| Removing a team member (A2 / L3) | `DELETE /api/team/members/{userId}` (OWNER) runs ONE transaction: delete that user's Sessions for THIS business, unlink the login from their StaffMember (`userId = NULL` and `bookable = false`, so clients stop booking someone who left; `active`, hours and appointments stay, the owner handles upcoming ones and can make them bookable again; the response carries `futureAppointments`, the count of upcoming active appointments on that entry. Going non-bookable only frees Free-plan capacity, so it can never hit a plan limit), delete any open invite for their email here, delete the Membership. The User row and their memberships and sessions in other businesses are never touched. Nothing is soft-deleted: re-inviting works through the normal invite flow (accept with the existing account) and creates a new non-bookable StaffMember. |
| Last owner and self-removal (A2) | The rule is the pure `checkRemoval` (domain); the SERVICE supplies it as a guard that runs INSIDE the removal transaction, after the business's OWNER memberships are locked (`SELECT … FOR UPDATE`, ordered by id), and the ACTING owner must still be in that locked set (otherwise 401, nothing written: a removed owner's in-flight request cannot remove anyone), so two owners removing each other at the same moment cannot both pass: the second sees one owner left and gets 409 `LAST_OWNER`. Removing yourself is 409 `CANNOT_REMOVE_SELF`. Another business's member, an unknown id and an already removed member are all 404. |
| User-row lock order (F36) | A login (or an invite accept by an existing user) verifies the password OUTSIDE any transaction, so it could insert its session after a reset / change-password had already deleted them. Fix: every such session insert and every password-changing transaction takes `SELECT … FROM "User" WHERE id = … FOR UPDATE` first (`lockUserPasswordHash`), and the login re-checks under the lock that the hash is still the one it verified, else the generic 401 `INVALID_CREDENTIALS` and no session. One lock, no extra round trip beyond it. **Lock order, always:** (1) a business's OWNER Membership rows (A2 removal), (2) the User row, (3) rows owned by the user (Session, EmailToken, Invite, Membership). `removeMember` never touches the User row, so no path takes (2) then (1); the login additionally takes `FOR SHARE` on its own Membership row after the User lock (so a racing removal cannot leave an orphan session), safe for the same reason. Change-password also compares the hash read under the lock with the hash it verified (else 400 on `currentPassword`, nothing written). Caveat: `emailToken.issue` inserts a row with an FK to User, which takes an implicit `FOR KEY SHARE` on the User row; a future transaction must therefore never take `FOR UPDATE` on the User after such an insert in the same transaction. Postgres 40P01 (deadlock) and 55P03 (lock timeout) map to 503 `SERVICE_BUSY` with Retry-After. |
| Session defense in depth (A2) | `sessionService.resolve` re-reads the Membership on EVERY request (role included), so a session row that somehow survives a removal is still a 401; an integration test deletes only the Membership row and shows the old cookie is rejected. Deleting the session rows in the same transaction keeps the table clean and means a re-added user cannot revive an old cookie. |
| Revoking an invite deletes the row (A2) | `DELETE /api/team/invites/{id}` (OWNER) deletes an unaccepted invite scoped by `businessId`; the public preview/accept then return the same 404 as for an unknown token. Accepted invites are kept (cleanup removes them later) and cannot be revoked (404). |
| Sign out other sessions (A2) | `POST /api/auth/sign-out-others` (any role) deletes every session of the caller in ALL businesses except the current one and returns `{ removed }`; limited per IP (`signOutOthersIp`, 20 / 10 min). The UI lives in the Settings Account card until F35 gives staff their own Account page. |
| Content-Security-Policy and security headers (F7) | The page policy is built per request in `src/proxy.ts` from the pure `buildCsp` (`src/lib/security/csp.ts`): `script-src 'self' 'nonce-<128-bit random>' 'strict-dynamic'` (`'unsafe-eval'` only outside production, never `'unsafe-inline'` for scripts), so only the scripts Next emits (it stamps the nonce, read from the REQUEST `Content-Security-Policy` header, on its own inline scripts; every route renders dynamically) and the chunks they load can run. `style-src` keeps `'unsafe-inline'` on purpose: React renders `style=""` attributes and Next injects `<style>`, and a nonce cannot cover attributes; the script policy is what stops XSS. `connect-src` is `'self'` plus the exact `https://<host>` parsed from `NEXT_PUBLIC_SENTRY_DSN` / `SENTRY_DSN` (the browser SDK posts straight to the EU ingest host; no wildcard; malformed or non-https values are ignored; if the tunnel F41 is built, remove the host). `frame-ancestors 'none'` plus `X-Frame-Options: DENY` is a DELIBERATE choice: the booking page cannot be embedded in another site's iframe. | WhatsApp via `wa.me` prefilled links | No paid Business API; the receptionist sends from their phone and the server records who sent it. |

| Fake providers in tests | The fakes record calls, which is how "sent exactly once" is asserted. |
| Login throttle: three dimensions in Postgres (`RateLimitBucket`) | Counted BEFORE the password check (atomic upsert, no read-then-write race): (1) email+IP 5 / 15 min, checked first so hammering one locked account never spends the NAT's budget; (2) IP 20 / 15 min across emails (skipped when the address is unknown); (3) email 30 / hour across IPs, a loose ceiling against rotating addresses. A success clears (1) and refunds its hits in (2) and (3) in the exact window they were taken. IPv6 is keyed by /64, IPv4-mapped addresses by their IPv4. Accepted residual risk: an attacker with many /64s can still burn a victim's 30 / h and lock that email for up to an hour; the alternative (no ceiling) is worse. | What gets reported | Server: only unexpected failures, from `withRoute`'s error mapper (non-AppError or status 500 or above, not `SERVICE_BUSY`) with tags `route` (the templated route such as `/api/staff/[id]`, never the URL), `requestId`, `businessId` (internal id, not personal data) and `method`; the job routes use the same mapper; render and action errors arrive through `onRequestError` in `src/instrumentation.ts`. Browser: unhandled errors and promise rejections, and render errors from `src/app/error.tsx` and `src/app/global-error.tsx` (an error with a Next `digest` happened on the server and is reported there, not twice). Never reported: AppError 4xx (validation, auth, not found, conflicts, rate limits), `redirect()` and `notFound()` control flow, AbortError, ResizeObserver loops, "Non-Error promise rejection", failed fetches, events whose stack is only browser extensions. Identical events are dropped and volume is capped (browser 50 per page load; server 100 per minute per instance). A missing i18n message in production is reported once per distinct key per page load as `reportMessage('warning', 'i18n missing message', { code, namespace, key, locale })`: key path and locale only. |
| Scrubbing (`src/lib/observability/scrub.ts`, unit-tested) | One pure module is the `beforeSend` and `beforeBreadcrumb` of both runtimes. Dropped entirely: the `user` object, cookies, every request header except `user-agent` (so no authorization, `x-cron-secret`, `x-csrf-*`), request bodies, query strings, env, local variables in stack frames, server name. URLs and paths become templates (`/l/[token]`, `/o/[token]`, `/o/[token]/leave`, `/pay/[token]`, `/invite/[token]`, `/verify-email/[token]`, `/reset-password/[token]`; `/b/[slug]` stays, query strings go). In exception messages, breadcrumbs, extra, contexts and tags: emails become `[email]`, phone numbers (E.164 and Lebanese local forms such as `03 123 456`, `71 123 456`) `[phone]`, opaque tokens of 32+ URL-safe characters `[token]`, values of password, secret, authorization, cookie and token-like keys `[redacted]`. Emails are matched with Unicode letters (Arabic and IDN addresses) after decoding `%40`, `&#64;` and `&commat;`. Phones are also caught after `/` and `-`, in `wa.me/`, `api.whatsapp.com/send?phone=`, `tel:` and `phone=` links. `/api/links|offers|invites|pay/<token>` are templated like the page routes, and any `body.signature` pair with both halves of 20+ characters becomes `[token]`. Prisma and Postgres errors are reduced to class, code and column names (`sanitizeError` before the SDK sees the object; the same reduction on the event), so validation arguments, `meta`, `detail`, `hint`, `where`, `query` and `parameters` never leave; a stray `Key (col)=(value)` loses its value; exception messages are cut at 500 characters. Dates, times (09:30), prices ($15), counts and Arabic text with digits are left alone. The walk is depth and size bounded and cycle safe; if scrubbing throws, the event is dropped. Breadcrumbs are limited to navigation, without data; console output is dropped entirely. `sdk.settings.infer_ip` is forced to `never`. Stack-frame code locations (`filename`, `abs_path`, `module`, `function`) are sanitised separately (`sanitizeCodePath`: home directories and signed tokens only, source context lines dropped), so stack traces stay readable. |
| Privacy wording and accepted limits | Personal data is removed on a best-effort basis (emails, phone numbers, link tokens and secret links, database error values). Free-text names cannot be detected automatically, so error messages are built without client data and Prisma / Postgres errors are reduced to class, code and column names. A rare residual risk remains and is documented in docs/ARCHITECTURE.md. Accepted gaps, each with a unit test or a note: (1) a client name inside a plain error message ("Booking for Rana Haddad") is not detectable, which is why our own `throw new Error` / `AppError` messages and logger calls were audited and carry no client data (see below); (2) a phone number with no `+` is recognised only as a Lebanese 8-digit number (01-09, 70-79, 81 prefixes), as `3 123 456`, as `00`/`961` forms, or as an 11-15 digit number with spaces or hyphens; an unseparated foreign number without `+` is not (it cannot be told from an id or timestamp); (3) third-party library messages we do not control. Audit result: no `throw new Error` / `new AppError` / `AppError.*` message in `src/server` or `src/app` interpolates client data (the only interpolations are `Invalid local time: <hh:mm>` and `Unknown EMAIL_PROVIDER / PAYMENT_PROVIDER "<config value>"`); every `logger.error` carries ids and `safeError` (name, code, message) and goes to pino logs, never to Sentry; email-send failures surface as static-message 503 AppErrors, not the provider's error. Keep Sentry's own data scrubber on (HUMAN_TASKS). |
